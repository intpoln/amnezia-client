# Тестирование

## Главное ограничение
На ПК пользователя обычно работает **официальный AmneziaVPN**. У сборки форка те же имена:
- канала `\\.\pipe\amneziavpn`,
- узла QtRO `AmneziaVpnIpcInterface`,
- служб `AmneziaVPN-service`, `AmneziaWGTunnel$AmneziaVPN`, `AmneziaVPNSplitTunnel`,
- устройства драйвера `\\.\MULLVADSPLITTUNNEL`,
- путей установки.

Поэтому **агенты никогда**:
- не запускают собранный `AmneziaVPN.exe`;
- не устанавливают и не регистрируют собранную службу или драйвер;
- не подключают VPN и не меняют маршруты, DNS и правила firewall.

**Агентам можно:** собирать проект и запускать unit-тесты (`ctest`). Тесты пишут настройки под отдельной тестовой организацией и службу не трогают, кроме `ConnectionTest`, который в форке не запускаем.

Реальное подключение проверяет **пользователь**: он выключает официальный клиент и ставит сборку форка. Виртуальной машины нет.

## Уровни проверки

### 1. Unit-тесты (агент)
```bat
fork\scripts\local-build.bat
fork\scripts\local-test.bat
fork\scripts\local-test.bat "^UiAppSTModelAndControllerTest$"
```
- Без аргумента `local-test.bat` запускает тот же набор безопасных тестов, что и CI. С аргументом — тесты по regex `ctest -R`.
- Для этой работы важны тесты `UiAppSTModelAndControllerTest` (`client/tests/testUiAppSTModelAndController.cpp`) и `SettingsSignalsTest`.
- Новая логика (сканер папок, хранение правил-папок) покрывается новыми тестами в `client/tests/`.
- Тесты, которым нужны секреты (`THIRD_PARTY_*`, `AMNEZIA_TEST_API_KEY`) или реальный VPN, не запускаем. Список безопасных тестов есть в `.github/workflows/fork-windows.yml`.

### 2. Ручная проверка (пользователь)
**Подготовка**, один раз:
1. В официальном клиенте экспортировать `.conf` нужных локаций Premium («Настройки» → Premium-сервер → «Configuration files»).
2. Желательно сделать резервную копию настроек: «Настройки» → «Резервное копирование».

**Каждая проверка:**
1. Отключить VPN в официальном клиенте и закрыть его, в том числе из трея.
2. Удалить официальный клиент. Настройки и список серверов остаются в реестре, и форк их подхватит.
3. Установить сборку форка: локальный установщик из `deploy\build\` или из GitHub Actions (запуск `Fork Windows build` → Artifacts).
4. Если Premium-сервер не подключается (в форке нет ключа шлюза), импортировать `.conf` локации.
5. Пройти чек-лист нужной задачи (ниже).
6. Если что-то не так, экспортировать логи в настройках клиента (раздел журналов) и передать агенту.
7. Вернуть официальный клиент: удалить сборку форка и установить официальную.

Формат хранения настроек у форка и официального клиента общий. Поэтому форк **не должен ломать официальному клиенту настройки**: новые данные кладём в отдельные ключи. Подробнее в [DECISIONS.md](DECISIONS.md).

## Чек-листы

### Исключение папок
- [ ] Добавить папку с игрой или программой. В списке одна строка с путём и числом найденных `.exe`.
- [ ] Подключиться. Программа из папки ходит мимо VPN, браузер вне папки — через VPN. Проверять по IP на сайте во встроенном браузере программы или по трафику в AppNetworkCounter/Resource Monitor.
- [ ] Добавить в папку новый `.exe` (скопировать любую утилиту), переподключиться: он тоже идёт мимо VPN.
- [ ] Удалить папку из списка, переподключиться: программа снова идёт через VPN.
- [ ] Выбрать очень большую папку (например, `C:\Program Files`): появляется предупреждение, интерфейс не зависает.
- [ ] Старые записи с отдельными `.exe` на месте и работают.
- [ ] После возврата на официальный клиент его список исключений не сломан.

### Стабильность
- [ ] Подключение и отключение 10 раз подряд: без зависаний, состояние в интерфейсе соответствует реальному.
- [ ] Недоступный сервер (временно поменять адрес в копии конфига): через 30–45 с ошибка, а не бесконечное «Подключение…».
- [ ] Сон и пробуждение при подключённом VPN: соединение восстанавливается.
- [ ] Wi-Fi и кабель одновременно: исключения работают.
- [ ] В логе видны времена этапов подключения.
